# PCB 追加布线分批工具

入口：[pcb_route_batch.py](pcb_route_batch.py)。测试：[test_pcb_route_batch.py](test_pcb_route_batch.py)。离线增量审计：[audit/README.md](audit/README.md)。

本工具把已规划、已审查的少量新线和新过孔分批追加到当前 PCB。**默认只编译，不访问 bridge、不占 EDA 锁、不修改 PCB。它不是自动布线器，也不负责计算净距、阻抗、载流或自动铺铜。**

只提供 `Line.create` / 贯通 `Via.create`，不提供删除、修改、移件、原理图同步、切窗口、开关文档、启动 bridge 或 `Via.modify`。项目 UUID 来自 `project.json`；PCB UUID 必须显式给出，不固化任何板子的 UUID。

## 输入和离线编译

准备当前项目目录内的资料：

- `project.json`：现有共享配置，按显式 `--project`、`EDA_PROJECT`、当前目录向上查找。
- `baseline.json`：公开 `getAll()` 导出的 `components` / `pads` / `lines` / `vias` 原生数组，及 `pcb_Layer.getAllLayers()` 的 `layers`。允许附带 `arcs` / `pours` / `regions`。元件和焊盘不能为空。
- `frozen-pcb-protel2.json`：`eda.pcb_Net.getNetlist('Protel2')` 返回的**非空原始字符串，或非空原始字符串列表**，用 JSON 保存并保留返回类型。单个字符串逐字精确比较；列表仅归一最外层顺序，每个成员必须是非空字符串，不去重、不裁剪或重写正文，不对字符串的字符排序。不要传原理图网表或 SHA 字符串，也不要自行把字符串包装为列表或从列表挑选某一板。
- `plan.json`：`{"coordinate_units":"mil","lines":[...],"vias":[...]}`。线字段为 `net,layer,startX,startY,endX,endY,lineWidth`；过孔字段为 `net,x,y,holeDiameter,diameter`。可带 `label` / `links` 等说明，`links` 仅作外部审查用途，工具不据此宣称物理连通。
- 独立几何/电气审查结果。工具的输入校验只确认非空已知网、有限数值、正宽度、合法孔盘尺寸、有效铜层、非零且为水平/垂直/45° 的线段、计划内无重复图元；**未完成实际净距审查的计划不能据此直接写板**。

下列命令在本仓库根目录下运行，用示意目录：`<项目目录>` 换成实际项目，`<工作区>` 是放共享锁的工作区根目录；同时替换当前已存在的 bridge 端口、明确板 UUID 和锁 owner。路径有空格时保留双引号。`--evidence` 必须是项目中的**全新目录**，证据不得放进共享工具仓库。

```text
python -X utf8 tools/pcb_route_batch.py --project "<项目目录>/project.json" --pcb-uuid "明确PCB_UUID" --bridge http://127.0.0.1:49620 --lock-file "<工作区>/.eda-lock.json" --owner "当前执行者" --baseline "<项目目录>/baseline.json" --frozen-netlist "<项目目录>/frozen-pcb-protel2.json" --plan "<项目目录>/plan.json" --evidence "<项目目录>/route-run-001"
```

不写模式参数就等价于 `--dry-run`。默认把线与过孔合在一起按**总数最多 20 个**分批；可用 `--batch-size 10` 缩小，不能大于 20。只允许基线 `layers` 中处于 SHOW/HIDDEN 状态（1/2）的 `SIGNAL` 铜层；未使用层和丝印/文档层被拒绝。

输出 `manifest.json`、复制冻结的三个输入、`compiled/batch-000.js` 等。

- 每批都包含项目/文档作用域、PCB Protel2 一致性，以及**所有现有元件/焊盘/线/孔的完整已序列化字段**门禁，不只是坐标或图元数量。`getAll()` 数组按 `primitiveId` 排序比较；对象字段顺序不影响结果，字段增删、值变化仍被拒绝。
- 第一批 JS 可具体展示完整基线。后续批次 JS 含 `__EXPECTED_FROM_PREVIOUS_VERIFIED_READBACK__` 占位符，因为新图元 ID 尚未产生。**不要把这些模板手动送入 EDA**；正式执行时工具从上一批独立验收的原生 snapshot 填入完整守卫。
- `manifest-sha256.json` 和输入哈希防止编译后内容被意外改写。要改计划，创建新证据目录重新编译，不能改已编译 run。

**网表类型也是冻结边界**：同一 run 中 `string` 与 `list[str]` 互换仍在写入前停止，即使某个列表成员与单个字符串完全相同。列表少一个板、少一个重复成员、混入非字符串或空字符串，也会停止。工具不会把当前单板返回当成旧多板返回的全集。若重启等操作改变了原始返回形态，执行者必须先独立核对当前项目/PCB、原始网表及实际几何，再以当前完整原始返回新建基线和 run；不能替换已编译 run 的冻结文件或绕过漂移门禁。空字符串、空列表、`null` 及混合类型列表均在离线编译前拒绝。

## 显式执行一批

先由实际执行者按工程规则取得/维护共享锁（工作区根目录下的 `.eda-lock.json`，所有 Agent 约定同一个位置），确认用户没有同时编辑本板。工具**不自动获取、不改写、不释放** `--lock-file`：它只接受与编译 owner 完全一致、scope 为 `project_uuid/pcb_uuid`、UTC 带时区 ISO8601 `heartbeat` 在 5 分钟内的现有锁。别人的锁、过期锁、缺失锁一律停止。

```text
python -X utf8 tools/pcb_route_batch.py --apply-one 0 --evidence "<项目目录>/route-run-001" --owner "当前执行者" --bridge http://127.0.0.1:49620
```

每次只执行指定的**下一批**，不自动执行所有后续批次。桥接地址必须显式给出，工具只验证已有本地 bridge 的 health；不会扫到另一个端口后自动改用、不会切换活动窗口。

执行顺序为：

1. 拒绝已失败/不完整 run 和重放，检查输入哈希、现有锁、bridge 身份和连接。
2. 在**同一个写调用的开头**核对项目、PCB、原始网表、全部已序列化四类图元字段；再次核对作用域后才逐个创建本批图元。
3. 保存完整 create 返回；立即另起 `/execute` 回读四类原生图元、其余几何数组、层和网表。
4. 验证所有旧对象完整字段不变，新增 ID 数量及种类恰好等于本批，新增对象字段符合计划。新坐标/宽度允许 `0.001 mil` 回读舍入误差，网名/层号/ID 精确匹配；该容差不是设计净距豁免。
5. 留下 `verified.json`，下一批仅能使用这次真实读回 snapshot。批次成功只表示**独立回读通过**，不表示已保存、DRC 已通过或可投产。


**当前门禁刻意保守**：原生拆线、改 ID 或超出上述容差的吸附，即使铜仍连通，也会因对象/几何不符而停止。停止是待复核状态，不能当作电气失败；用 [pcb_route_diff](audit/README.md) 分离 ID 变化与实际位移，再核对实际铜覆盖、网络和 DRC。确认后按下方错误恢复流程重建基线与新 run，不能删除阻断标记强行续跑。

同一个证据 run 内的命令用临时 `ACTIVE.json` 串行化；它不是 EDA 共享锁。所有命令请求、完整响应、错误、created、snapshot 和网表均以独占创建写入 `live/apply-000/` 等目录，stdout 只打印统计摘要，不把大网表刷屏。原生 `created.json` / `snapshot.json` 可直接交给 [pcb_route_diff.py](audit/pcb_route_diff.py) 做独立增量审计。

## 保存检查点

先按项目流程重建已有铺铜并完成本批该做的检查。工具的检查点**不会自动重建或改变 Pour**，也不会清除错误标记。

```text
python -X utf8 tools/pcb_route_batch.py --checkpoint --evidence "<项目目录>/route-run-001" --owner "当前执行者" --bridge http://127.0.0.1:49620
```

调用严格分开：作用域/几何/网表守卫 → `pcb_Document.save(明确PCB_UUID)`；**另起调用**独立 snapshot + 网表；再**另起调用** `pcb_Drc.check(true,false,true)`。不关闭重开。完整结果保存在 `live/checkpoint-after-NNN/`。

DRC 返回 `false` / `null` / 非列表时停止，绝不视为零错误；非空错误列表完整保留，摘要明确 `drc_is_clean:false`。`CHECKPOINT_CAPTURED` 表示检查证据已收集，不代表所有 DRC 已清零。按用户规则，大动作、异常或持久化存疑需人工采用手册的加强验收，不能靠此普通小批工具代替。

### 界面错误标记收尾（检查点之后）

清除画布上的 DRC 叉号是**界面收尾**，必须排在保存、独立回读和真实 DRC 结果归档之后；清屏不会修复错误，也不能覆盖或替代刚保存的 DRC 报告。按下面顺序执行：

1. 确认本批检查点目录已经包含保存响应、独立 snapshot/网表和完整原生 DRC 响应。
2. 读取 `sys_ShortcutKey.getShortcutKeys(true)`，按标题“清除错误”核对**当前用户映射**。快捷键各人可能自配，不能跨环境硬编码，以你环境里查到的映射为准。
3. 使用已获授权的 Computer Use 界面操作向 EasyEDA 发送核对后的按键，再观察画布，确认错误叉号确实消失。按钮回退同样必须重新定位并观察结果。
4. 在项目证据目录记录 `pending`、`completed` 或 `skipped`：只有实际发键且观察到叉号消失才可写 `completed`；尚未做界面操作写 `pending`；明确决定保留标记且不影响观察写 `skipped`，并写原因。建议最小记录为 `{"status":"pending|completed|skipped","shortcut":["<查到的按键>"],"shortcut_verified":true,"ui_observed":false,"reason":"..."}`。

Python 包装脚本可以查询并保存快捷键映射，但**不能独自发送原生按键或证明界面已清屏**。公开 API 未验证存在 DRC clear 方法，不得虚构 `PCB_Drc.clear`。如果当前没有界面操作授权或无法可靠观察，就保留 `pending`，不要把脚本成功、快捷键查询结果或 `ui_observed:false` 写成 `completed`。

## 当前用户要求不主动保存时

`--checkpoint` 会调用保存接口。若当前用户取消“主动保存/关闭重开”验证，不调用该模式；继续使用 `--apply-one` 自带的独立回读，再由项目只读包装器分别抓取对象/网表和原生 DRC，保留实际证据。云端自动保存方式与 API 缓存缺陷是不同事实，未做的持久化验证不能写成已通过。项目包装器可显式阻止 checkpoint，防止下一轮误用；共享工具的默认语义不因此改变。

## 超时、错误或进程中断

**没有自动重试、没有自动重放。** 超时/HTTP 500/异常可能已执行部分图元；工具保存完整错误，写 `BLOCKED.json`，后续 apply/checkpoint 均拒绝。即便进程被杀死来不及写 BLOCKED，未完成的 live 目录或残留 ACTIVE 也阻止继续。

下一步是由执行者独立只读检查当前板子和原始响应，确认哪些对象已存在，重新导出基线/冻结网表，只为已确认缺失的对象编制新计划并使用全新证据目录。不要删除失败标记或旧证据来“解锁重跑”。

**实板验证摘要（2026-09-11 / 12，在一块多层板上实测；实测记录未公开，这里只留结论）**

1. **正常小批**：`--apply-one` / `--checkpoint` 首次完整实板运行成功。单批追加 11 条线和 3 个贯通过孔，创建返回与独立回读全部匹配，旧元件/焊盘/线/孔的已序列化字段均不变；保存 → 独立 snapshot/网表 → 原生 DRC 分开调用，原始请求与响应都有记录。独立差异审计没有坐标偏移；唯一差异是 3 个过孔的 `designRuleBlindViaName` 从创建返回的 `null` 变为回读的空字符串——**这项 metadata 差异完整保留在报告里，不能推广为忽略其它字段变化**。（此前 2026-09-11 对一份已有计划只做了纯 dry-run 回归，未应用。）
2. **原生拆线触发保守停止**：请求 1 条 0.30 mm 长线跨过 6 个同网焊盘；原生返回 1 个 ID，独立 snapshot 却是相邻焊盘间 5 段，返回的 ID 已不存在。工具以 `Unexpected added or missing primitives: lines` 停止，留下 `UNCERTAIN_DO_NOT_REPLAY`/`BLOCKED.json`，未重试。独立核对：旧四类图元不变，5 段与请求线的铜覆盖对称差为 0，保存后 5 组连接和净距检查通过。**停止可能是原生拆分引起的待复核状态，不能只按返回数或 ID 判成断线，也不能据此跳过门禁。** 恢复时按实际铜覆盖、网络、净距及原生 DRC 复核，重新导出 snapshot/网表建新 run，只补确认缺失的图元；不重放旧 run、不删失败标记。以独立回读为新基线的续跑 run 完成了保存/独立回读/原生 DRC 留证，原 5 段全部保留。1→5 不是所有 create 的规律。
3. **保存 → 关闭 → 重开**：拆出的 5 段仍在，ID、端点、网络保留；线宽由 11.811023622… mil 按存储精度规范化为 11.811 mil——**不能把初次回读的零覆盖差扩大为重开后字段逐字节不变**。总项目 Protel2 原字符串列表仅排序最外层后，改前、重开前、重开后 SHA 一致。统计铜线只算启用铜层，`Line.getAll()` 的全层总数还含丝印/文档线。
4. **单字符串 Protel2**：兼容修复离线回归后，在原生网表返回非空单字符串的环境中实板执行成功：单批 9 条线、0 个过孔，旧四类图元完整字段不变，原始字符串网表正文一致；目标物理连接全部通过，本批最小净距按实际新增铜几何与显式障碍核对。string/list 跨类型漂移门禁不因此放宽。
5. **同一 run 连续多批**：一组信号线连续执行 7 批（前 6 批各 20 图元、末批 3 个），每批独立回读通过才继续下一批；孔参数直接采用已核对的实际尺寸，没有重放此前因量化差异 blocked 的 run。之后用户取消了主动保存/重开，此后的增量按当时偏好验收，不把历史保存验证扩展到后续修改。

**边界**：各次检查点都明确 `drc_is_clean:false`（原生 DRC 无 Clearance 项，但仍有未布通项）。以上证明的是命令流程、各批回读和已实施范围的保存重开，**不是全板 DRC 通过、云端持久化证明或制造放行**。常规小批按流程未关闭重开；异常/大动作仍按加强验收。其它板型、其它版本和其它原生改 ID/吸附的恢复情况仍需对应验证。**22 项离线测试是门禁回归，不能代替实板验证；单次执行耗时也推不出普遍提速倍数。**
