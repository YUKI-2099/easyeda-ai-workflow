## 0. 环境与启动

### 0.1 组成

```
AI Agent ◄─HTTP/WS─► Bridge Server(Node,本机,49620-29) ◄─WebSocket─► EasyEDA Pro(lceda-pro)
```

本文实测基于 skill v1.1.3、扩展 **Run API Gateway** v1.0.5、EDA 3.2.149.88089769。**2026-09-10 复核与 07-29 一字不差**,§1 全部结论适用。
若在多个 agent 工具里各装一份 skill(如 Claude Code 的 `~/.claude/skills/`、OpenCode 的 `~/.config/opencode/skills/`、Codex 的 `~/.codex/skills/`),各份保持同一版本。
装依赖(每份一次):`cd <skill 目录> && npm install`(如 `~/.claude/skills/easyeda-api`)。

### 0.2 起 Bridge

**先扫现有服务/监听,再按项目规矩决定能不能自己起**:项目不许 AI 自行起进程时,扫不到就报告用户,不能擅自起进程或装依赖;用户为某一次启动给的授权只管那一次。装了多份 skill 时各份的依赖可能不同,脚本存在不等于能跑;报 `ERR_MODULE_NOT_FOUND: ws` 时先找依赖齐全的那份来起,不要重复安装,也不要重复起 Bridge(#52)。

**必须后台跑**,前台会把 AI 阻塞住:`cd "$HOME/.claude/skills/easyeda-api" && node scripts/bridge-server.mjs`(skill 装在别处就换成那个目录)
端口取 `49620-49629` 第一个空闲的。找它:

```bash
for p in $(seq 49620 49629); do curl -s -m 2 http://localhost:$p/health | grep -q easyeda-bridge && echo "BRIDGE=$p"; done
```

### 0.3 🚨 启动与重连:**先 Bridge 就绪,再连接扩展**

不要仅靠等待自动重试:2026-07-29 实证,扩展已启用后才起 Bridge,等 60s `edaWindowCount` 仍为 0;该记录不能推导为界面没有主动重连入口。

**有现成菜单时优先重连**:Bridge 已就绪后,在现有 **API Gateway → 重新连接** 点击;2026-09-12 实测从0窗口恢复到1窗口,**无需先停用/启用扩展或重启 EasyEDA**。菜单不可用或重连失败时,再考虑扩展管理器的停用→启用或重启。
**未找到已验证的公开 API 可主动触发重连,不等于 UI 没有“重新连接”按钮。** 界面操作可由用户或已获本次操作授权的 AI 完成;不要因缺 API 就要求用户先重启软件。成功提示后还要核对 `/health` 的服务身份、`edaConnected:true`/窗口数,刷新 windowId,再独立断言目标工程/文档作用域,不能只凭 Toast 判定恢复完成。
顺带确认扩展的「外部交互」权限勾上了,否则连不了 WebSocket。

### 0.4 连上之后确认三件事

```bash
curl -s http://localhost:49620/health        # edaConnected: true
curl -s http://localhost:49620/eda-windows   # count / activeWindowId
```

0 个窗口 → 回 §0.3。1 个窗口 → 自动选中,**`POST /eda-windows/select` 用不上也不该用**(㊿)。
2+ 个窗口 → 必须先 `POST /eda-windows/select {"windowId":"..."}`,不要靠默认(旧工具时代因"打到另一块板"出过删错件事故)。

### 0.5 🚨 skill 可以装多份,但只能有一个 Bridge

EasyEDA 扩展全局只连一个 Bridge。**第二个 Bridge 会占到下一个空闲端口,`/health` 正常返回但 `edaWindowCount` 恒为 0**
→ 看起来像"EDA 没开",实际是连错了那一个。这个误判很难自查,因为两边都"正常"。

**规矩:任何 AI(包括被拉来审查的 Codex)在起 Bridge 之前,必须先用 §0.2 那行扫端口找现成的。** 扫不到才轮到"起一个"。脚本里用 `tools/bridge.py` 的 `find_bridge()`;`python tools/bridge.py` 直接打印找到的地址与 health。

### 0.6 skill 是只读依赖,不是我们的文档

🔴 **永远不要把踩坑记录写进 skill 目录**:它是 ClawHub 上别人发布的带版本包(`.clawhub/origin.json` 有 fingerprint),升级整包覆盖;装了多份时各份必然漂移。
**skill = 说明书(厂家的,会被换掉)｜本文 = 病历(我们的,一直累加)。** 让 AI 找到本文的正路,是在各 agent 的入口文件(工作区的 `AGENTS.md`、`CLAUDE.md` 等)里写一行指向本文。

**唯一的例外(可选)——一段"入口补丁"**(改原 skill、不新增 skill:新 skill 会和厂家 skill 抢同一批触发词,调用时冲突):
在每份 `SKILL.md` 的「Command Triggers」之后插入同一段以 `<!-- BEGIN local-patch ... -->` / `<!-- END local-patch -->` 包住的十来行,只做一件事——**告诉 AI 先读本文、先扫端口找现成 Bridge**,不放任何坑记录。各份内容字节一致。
这只是**可选的便利工具**:不打补丁,靠入口文件指向本文也一样用。`python -X utf8 tools/patch_easyeda_skill.py` 默认只预览、不写文件;确认后加 `--apply` 才写,写前自动备份原文件;补丁里写的手册路径按本仓库的实际位置算,不用手改,所以要从你长期用的那份仓库跑,别从临时副本跑(临时目录下的副本会拒绝 `--apply`);幂等,找到的各份一起打,打完自校验。默认找 `~/.claude`、`~/.config/opencode`、`~/.codex` 下的 skill(认 `CLAUDE_CONFIG_DIR`、`XDG_CONFIG_HOME`、`CODEX_HOME`),也可以用 `--skill <路径>` 指定;指定的路径不存在时报错退出、一份都不写。
补丁会被 skill 升级覆盖,所以**升级 skill 之后**重跑一次,再重跑一遍 §1 的坑看哪些修好了,记进 §8。

## 1.6 🚨 多 Agent 并发写入纪律

**危险来自架构:Bridge 单例,`activeWindowId` 和"当前文档"是全局状态,没有锁。** 三种事故:同时写同一页互相覆盖;对方切走窗口/文档 → **写到错误的页甚至错误的工程**(通用手册 §1-1 血案);验证时读到对方的中途状态。

## 1.7 🔴 画原理图的标准流程(2026-07-29 实测跑通,别再自己试)

> 官方 skill 只有 API 参考,**没有"怎么画一张图"的工作流**。下面这套照做即可,不要即兴发挥。

**知识来源(可选参考)**:已停用的社区 `easyeda-agent` skill 在 `references/` 里有几份**纯几何约定,与 API 无关**:`schematic-layout-conventions.md`(分区/间距/短桩/朝向,**最值钱**)、`orientation.json`、`auto-layout-sop.md`、`standard-parts.json`、`pcb-layout-conventions.md`,按它画过多块实物板。手上有这个旧包就对照着读(旧 CLI 命令作废,几何约定照读);没有也不影响——**要点已写进本节**(行式布局模板、短桩长度与朝向表、§1.7.9 摆放四规)。

**🚨 最关键:引脚必须用非零 wire 引出,标志不能压在引脚上**——「EasyEDA 的 DRC 不认重叠点为连接」。压在引脚上的后果:网表看着连上了,**DRC 判 fatalError**,而 `getNetlistFile()` 有 fatal 时返回 `undefined`(⑬)。**一律以 DRC 为准。**

### 标准流程(逐步)


### 1.7.9 🔴 摆放四规(2026-07-31 用户重摆后逐条纠正,**全是我犯过的**)

① **短桩就是 10~30,不许靠拉长去躲标签**——标签挤的正解是错开行(改 y),不是拉长线(改 x)。
② **多端/异向引脚的器件(MOS、三极管、稳压管)放在功能块的最顶或最底**,单独留行距;两脚横排件中间 40 行距整齐排;连接器最顶紧邻自己的电路。**这正是坑 ⑳ 全板短路的同款几何——布局挤 = 画短路的温床。**
③ **用户丢过来的器件是「料」不是「位置」**:挪到它自己的电路块旁,成对器件相邻摆,一个功能块的所有件聚在一起。
④ **竖脚符号的两脚件转 90° 摆横**:放完一批回读 `pin.x` 是否两两不同,竖脚的一律转。这直接消灭 ⑳ 的成因。
**验收**:用户重摆后逐网对比冻结网表——无极性件 pin1/pin2 对调无害;**有极性件(电解、二极管、LED)对调就是致命的**。

### 1.7.11 原理图整组平移与版式重排（2026-09-14 实测）

**2026-09-27 合并补充**：本节记录的是 09-14 经小步验证的源字段受控平移。若采用逐图元 API 重建路径，必须同时遵守 #60～#63：不用 netFlag/netPort X/Y setter 或 Wire.modify 平移；对已确认完整且备份的目标子电路，分阶段处理旧线与新线，避免边删边建相互合并。不得把局部受控重建理解成允许全图批量删线，也不得将两条操作路径混用后沿用旧验证结论。

配合通用手册 §7.2；当前实测客户端3.2.149.88089769。先冻结当前源、getAll对象、实际引脚坐标和Protel2网表，再按**引脚—导线端点—网络符号**建立每件器件的几何组。若一根线关联多个器件或归属不唯一，停止自动平移该组，改按完整子电路处理；不按“离谁最近”猜归属。

- 本次getter中元件/引脚Y向上，页源码`COMPONENT/ATTR/TEXT.y`及`LINE.startY/endY`符号相反；使用前对照真实对象逐项断言，不能把源码文档的示例字段当成当前运行时字段。源码中导线由`WIRE`＋`LINE.lineGroup`组成，getter折线仍按坑㊷的独立四元组解析。
- 移动组包括COMPONENT、其本体/引脚所属ATTR、导线LINE及其ATTR、netFlag/netPort与相应属性；只变坐标/图面文字，不重建器件，不写库引用键。不用已知会清空网名的netPort X/Y setter（坑㉘）。
- `setDocumentSource`可用于**已读懂当前格式、受控字段修改且备份完整**的重排；先单组小步试验，独立读取原始字段及网表再扩批。不能把“返回true”或画布变化当持久化证明；最终仍需原生DRC、独立几何/身份/逐脚网表对账，以及按大动作规则保存重开验收。不可泛化为对任意项目源整包回写都安全。
- 写前同时核网表和当前源对象。实测连续只读导出会改变`DOCHEAD.client/updateTime/version`，但所有图元不变：仅这些日志头字段变化可单独识别并保留最新头，**不可因此忽略图元/属性/连线的真实差异**。本次检测到用户修改接口附近标志/引线时，护栏确实阻断了下一批，保留了人工改动。
- 单组试验和整页平移后，独立源回读/网表与几何三查通过；验证只覆盖本次对象类型与纯平移。新增无电气分区边框使用RECT形状，不能用WIRE画框。物料字段纠错会进入网表，须另列准确位号/字段/旧值/新值白名单，禁止笼统忽略属性变化。

实测记录未公开。实现方式是参考做法(尚未通用化,未收进 `tools/`):拆成三段脚本——准备(冻结源、对象、引脚坐标和网表,建几何组)→ 平移(先单组 canary,再整页)→ 收尾核验(源回读、网表、几何三查)。这类脚本写死了某个工程的作用域,只能照方法重写,禁止原样回放到另一张图。厂家 skill 保持只读。

**2026-10-07 补充:几种参考做法**(一轮原理图审查后改图时用过;尚未通用化,未收进 `tools/`。下面只写方法,自己实现时按当前工程重取作用域,别套别的工程的页 uuid):

### 2.10 🔴 三脚以上器件:**放下去、读引脚名、再连线**

`getAllPinsByPrimitiveId()` 每脚有 **`pinName`**(不是 `name`)。两个反直觉实证:`2N7002` 是 `p1=G(左) p2=S(上) p3=D(下)`(猜会接反 → MOS 永远导通);`BAT54` 单只 `p1=A p3=K p2=NC`。
**判据**:读出**有功能名**(G/S/D、A/K、VDD/SCL)→ 可连;读出**只有数字** → 等同纯数字连接器,**必须拿到实物/手册/已验证板网表之一才能接**,拿不到留 NC 并列入必核清单。
💡 反过来当选型标准:同功能的料优先挑**符号有功能名**的(`BAT54S` 只有 1/2/3,两只单管 `BAT54` 有 A/K,器件数一样歧义归零)。

### 2.11 🔴 两个来源打架时,**删掉依赖**,不要二选一

`BAT54S` 公共脚:手册说 pin2,符号画法像 pin3,没有第三来源仲裁。选择不是赌一个,而是**换成不依赖该结论的方案**(单只高边二极管,两脚器件歧义消失)。
**在两个可信度相当、结论相反的来源之间做选择就是在赌;先问「有没有一种做法根本不需要知道这个答案」。**

### 2.12 连线布局:**让交叉在结构上不可能**

①同一功能块内所有短桩走水平且各在不同 y → 没有竖直段 → 物理上不可能交叉;②引脚密集的连接器:水平出线 → 竖直分散 → 40 间距端口列,**保持上下顺序**则拐点 x 递减即不交叉(㊲);③往已有区域连线前先扫障碍并**照抄该区域已有约定**(如「10 单位短桩 + 端口统一对齐在同一个 x」),比自创安全。

### 2.13 🔴🔴 安全断言本身必须被测试

## 3. 🚨 永久拉黑清单(每条都有事故背书,新工具没有 undo,风险与旧工具完全一样)

| 禁用 | 新 API 里的名字 | 原因 |
|---|---|---|
| **原理图→PCB 整体同步(往已有布局的板子)** | `pcb_Document.importChanges()` / `sch_Document.importChanges()` | 📖 曾**整板重摆几乎全部器件(两百多件),含已锁定的接口件**。网络同步只允许逐件/逐网/逐绑定 |
| **批量删线** | `sch_PrimitiveWire.delete([多个])` | 📖 检查器的"零长线/dangling"分类会把**活连接**误标。逐根删 + 每删即查网表 diff。**API 无 undo** |
| **绑定异常时 reload/save** | `*_Document.save()` | 📖 会把损坏状态**固化**,重开后丢件(血案:十几件全丢) |
| **用户 GUI 活跃编辑时对同一文档写** | 全部写接口 | 📖 该时段 API 读数可能陈旧自相矛盾。**用户现场永远优先** |
| **用户开始布线后移动任何器件** | `toAsync().setState_X/Y()` | 📖 布线开始后坐标真源 = 用户走线。**唯一例外**:用户明确要求「连线一起整体挪」(如接口坐标取整),按 PCB 手册 §3.8 把器件和连通的铜一起平移(先删光块内线再重建,坑 #82) |

**`importChanges` 的范围澄清(2026-07-30,限定不是推翻)**:血案机理是「重摆已存在的器件」;**往完全空的 PCB 首次导入不适用**——且新 API 的 `pcb_PrimitiveComponent.create()` 只放封装、不带位号/uniqueId/网络绑定,逐件加得一堆孤儿件,**所以首次上板只能走 `importChanges` + 用户点确认弹窗**(㉑)。执行纪律:调用前断言 ①当前文档是目标 PCB ②`getAllPrimitiveId().length===0`;调用后独立复读器件数并与原理图对账。用户已同意但人不在电脑前(经 SSH 远程作业)时,可按 #85 由 AI 截图看清弹窗后代点。

**写前双断言在新工具下更重要**(`windowId` 会漂):任何写操作前程序性 assert 工程 uuid 与页 uuid(§1.6 防线 1)。**断言失败即终止,不许"接着试试"。**

## 4. 提速与熟练度进化

### 4.1 基准(2026-09-10,一份几页、一百多件、几百根线和几百个符号的原理图,单次会话画完并审计)

| 动作 | 实测 |
|---|---|
| `/execute` 空往返 / 硬超时 | ~210ms(含 curl 启动)/ **30s 不可配** |
| 行式 helper:放件+设位号+补 Value+两侧短桩+两侧符号,6 件一批 | **20~27s / 批** |
| 芯片扇出:14 引脚一次调用(读脚→折线→端口列) | **10~18s / 颗** |
| 建页(create→改名→改图纸→回读)/ 全图网表导出 | ~7s / ~2.5s |
| 清全部导线网名 | ~3.5 分钟 |

**用户口径:比上一轮"快了不止 10 倍"**,来自三件事:①「一行」和「一颗芯片扇出」封装成数据表驱动的 helper,只写规格 JSON;②验收全部机械化(网表回读 + 与上一版冻结逐脚 diff + 几何三查),不靠看图;③批量卡在 30s 内(6 件/批)避免 500 后返工。
**方法上最值钱的一条:画完全图后与上一版冻结网表做逐脚 diff**(复用件几百个脚差异 0),比任何目视检查都硬,脚本 20 行。

### 4.2 🔴 核心提速姿势:**一次 `/execute` 塞进一整段状态机**

新工具是在 EDA 里直接跑 JS,「查状态→循环放件→循环接线→回读断言」可写进一次调用,中间步骤连 HTTP 都不走。
但受 30s 约束:太碎 → 每步 210ms 往返且 AI 每步回模型;太大 → 撞超时停中间态。**经验批量**:放件 15~20 件/次;画线+标志 20~25 条/次;纯读单独一次不和写混;含"放件+接线"的复合批 ≤6 件。
**每批必带**:①开头 scope 断言(§1.6);②幂等——先读现状,已存在的跳过;③结尾回读本批改动;④`return` 结构化摘要(成功/跳过/失败明细),别 return 大数组撑爆上下文。
**末端总账**:导网表 → 离线跑通用手册 §10.1 不变量 + 几何三查(㊵)→ DRC → 记 SHA256 → 与上一版冻结逐脚 diff。

### 4.3 经验积累的规矩

- **API 签名不许猜**:`<skill>/references/classes/<类名>.md` 里没有的方法就是不存在;`Promise<>` 必须 await。
- **文档说的和运行时不一致时以运行时为准**,当天回填 §1(枚举、obsolete 的 getNetlist、pcb_Drc 在原理图页 500——这类矛盾大概率还有)。
- 🔴 **写操作的返回值必须接住、进日志、作断言依据**;日志打"我想做什么"而不打"API 说了什么",一批失败看起来全是成功(⑪)。
- 🔴 **判定"某个 API 坏了"之前,先换一条独立路径复验**——建档当天就因跳过这步得出过两次错误结论(⑨ ⑪)。**宁可多花一次调用。**
- 🔴 **审查方的转述不能替代自己核**(㉟ ㊿):"1 warn 是 XX"、"距离是 658"这类数字,谁说的谁给出处,没出处就自己拉。
- **每次踩到新坑当天补进 §1**,带日期 + 实证;**验证过的 ⚠️ 立刻升级或推翻**。

1. **Bridge 是单例,两个 AI 共用一个。** `activeWindowId` 是全局状态。**单窗口时 `select` 用不上也不该用;多窗口时约定不许 select**。真正会干扰的是 `openDocument` 切页 → 一次只让一个 agent 用桥接(㊿,§6.4)。

### 6.4 🔴 让审查方自己拉数据(2026-09-11 实测,比喂它导出结果有价值得多)

**协议**:执行者在审查时段完全不碰桥接;审查者允许 `openDocument` 切页读、所有 `get*`、`sch_Drc`;禁止写、禁止开 PCB、禁止 select;开工先记 `getCurrentDocumentInfo()`,做完 `activateDocument(原 tabId)` **还原到运行前的文档**并回读确认(#51;切回用户已开的 PCB 标签页只是激活 tab,不算开 PCB);跑之前确认用户不在 GUI。
**审查者必做**:①现场重导网表算 SHA 与冻结比——🔴 **按原始字节算**:同一份网表用 `read_bytes()` 读,和用 `read_text()` 读再 `.encode()`,字节数和 SHA 都对不上,差的字节数恰好等于文件里 CRLF 的个数——**换行归一化不是文件变更**;"原始字节一致 / 规范化文本一致 / 网表语义一致"是三个不同结论;②**自写解析器**(不许 import 执行者的,格式细节见 ㊺)重算件数/网数/逐脚,与执行者的导出逐项比;③几何三查 live 拉(网表看不出);④NC 标记核查;⑤DRC 自己跑(㊾);⑥重复位号与属性审计(㊸ 的"来源判定"边界)。
**本地解释器先定位再用**:审查方的环境里 `python` 不在 PATH、`py -3` 说没装、旧 venv 指向已删掉的 Python 都遇到过——**venv 文件存在不等于能运行**;Codex runtime 自带的解释器也能用。定位并验证实际解释器 + UTF-8 输出,不必遇到 PATH 缺失就装一套新环境。
**为什么值得**:同一个解析器出的数两边一起错。2026-09-11 那一轮机器数据差异 0,审查方却抓出执行者统计口径/前提/推论 17 处问题——包括执行者自己刚订正过一次的跨板拓扑**仍然是错的**。
